# Agent learning loop

Status: design draft for approval. Nothing is built.

## Intent

A new agent is not autonomous on day one. A human colleague becomes autonomous by learning how the company works, what reviewers push back on, how to debug recurring problems, and by dropping beliefs that turned out wrong. Paperclip agents need the same loop: learn from every task, keep what proves true, and unlearn what stops being true, without a human editing instructions by hand.

Each agent has one role and keeps its learning to itself. There is no company-wide promotion path in this design.

## What exists today

- Every managed agent has a persistent directory (`AGENT_HOME`) with an entry file (`AGENTS.md` by default) and free-form files (`doc/agent-files.md`).
- Only the entry file's content is placed in the system prompt. Sibling files are named by path and the agent has to choose to open them (`packages/adapters/claude-local/src/server/execute.ts:518-527`). No code loads notes into the prompt.
- No instruction tells a non-CEO agent to read notes at the start of a run or write learnings at the end. The CEO's `HEARTBEAT.md` is the only example.
- An agent may edit its own managed files without a confirmation, unless it holds only a suggest-only grant (`server/src/services/authorization.ts:2728`). Protecting `AGENTS.md` from self-edits is therefore a convention, not an enforced rule.
- A reviewer's request for changes already wakes the executor with `execution_changes_requested` (`server/src/routes/issues.ts:3031`). `agent.run.finished` and `issue.updated` are published to plugins. Routine triggers are only schedule, webhook and API.
- The Reflection Coach proposes `AGENTS.md` and skill diffs from trajectories, behind a `request_confirmation`. It is event-less and its weekly routine is paused by default.
- `skills/para-memory-files` gives agents a memory structure but is not tied to any trigger.

## Goals

1. After each task that taught the agent something, the agent records it in its own directory, with evidence.
2. At the start of every run the agent sees a short index of its learnings without having to remember to look.
3. When new evidence contradicts a recorded learning, the agent retires or replaces that learning in the same step. Unlearning is part of learning.
4. Learnings are inspectable and reversible by a human at any time.
5. Learning is provably effective, through an eval.

## Non-goals

- Sharing learnings across agents or promoting them to company level.
- Replacing the Reflection Coach. It keeps proposing `AGENTS.md` and skill changes; this loop is the agent's own, cheaper, ungated layer beneath it.
- A new database table, API or UI for v1.
- Semantic or vector retrieval. An index file is enough while an agent holds tens of learnings.

## Anti-goals (what would make this a failure even if it works)

- Memory that only grows. An agent that never retires anything is worse after six months than on day one.
- A learning with no evidence behind it, or an inferred one stated as fact.
- A wrong self-written rule that silently changes the agent's role, boundaries or approval behavior.
- Learning writes on every routine success. This burns tokens and adds noise.

## Design

### Layout (inside `AGENT_HOME`)

```
AGENTS.md                      role, boundaries, hard rules. The agent does not edit it as part of learning.
learnings/INDEX.md             one line per active learning. Regenerated by the agent on every change.
learnings/<slug>.md            one active learning.
learnings/retired/<slug>.md    tombstone: the retired claim, why it was retired, what replaced it.
playbooks/<slug>.md            procedures for recurring situations (how to debug X, how to handle Y).
```

Splitting by lifecycle is deliberate. `AGENTS.md` changes rarely and is gated. Learnings change often and are cheap. One file per learning means one lesson can be retired without rewriting a blob.

### Learning entry format

Frontmatter: `claim`, `kind` (`fact` | `preference` | `pitfall`), `evidence` (issue or comment links, at least one), `learned_at`, `last_confirmed`, `confirmations` (count). Body: when it applies and what to do. A learning without evidence is not written.

A playbook has the same frontmatter plus `applies_when`, and a numbered procedure in the body.

### Read side

The server adds a bounded `learnings/INDEX.md` to the per-run prompt guidance returned by `instructionWorkingCopyGuidance` (`server/src/services/agent-instruction-working-copies.ts:76`). This is the single shared point for every adapter, native and remote sessions included.

- The index goes in the per-run prompt, not the system prompt. The Claude adapter keeps the system prompt content-addressed and refreshes only the path directive per turn (`packages/adapters/claude-local/src/server/execute.ts:513-516`), so an index in the system prompt would go stale on resumed sessions.
- The index is capped. Over the cap, the server truncates and adds a line telling the agent the index is incomplete and to consolidate it.
- The agent opens individual entries and playbooks as needed. Only the index is injected.

### Write side: reflect and reconcile

A step is added to the `paperclip` skill's task procedure, before an issue moves to `in_review` or `done`, and when waking on `execution_changes_requested`:

1. Did this task involve a surprise, a correction (reviewer or human), a retry, or a failure that was then recovered? If not, write nothing and stop. The gate applies to writing new learnings only. At any point in a task, if the agent applies a learning and finds it no longer holds, it reconciles that entry immediately, with the evidence from the task at hand.
2. For each candidate lesson, check `learnings/INDEX.md`:
   - **Confirms** an existing entry: bump `last_confirmed` and `confirmations`.
   - **Contradicts** an existing entry: move it to `learnings/retired/` with the reason and a link to the contradicting evidence, and write the replacement.
   - **New**: write an entry with evidence.
3. Regenerate `INDEX.md`.

The wake on `execution_changes_requested` is the primary capture point because the reviewer's feedback is the strongest evidence an agent gets.

### Unlearning

- Contradiction is handled in the reconcile step above.
- Staleness is a read-time rule, so the server never parses entry files. Each `INDEX.md` line carries the entry's `last_confirmed` date. The skill tells the agent that an entry whose date is more than 90 days before today is not applied blindly: the agent verifies it against current evidence first, then confirms it (bumping the date) or retires it. An idle agent therefore marks nothing, and nothing needs to. Retired entries are never deleted automatically.
- Retirement keeps the tombstone, so a mistaken unlearn can be reverted by moving the file back.

### Boundaries

- Learning writes only to `learnings/` and `playbooks/`. The skill states that the agent does not edit `AGENTS.md`, the profile, or skills through this loop. Changes to those surfaces stay with the Reflection Coach path and its `request_confirmation`.
- Entries must not contain secrets or personal data. The skill says so and the agent redacts before writing.
- Learnings stay within one agent and one company. They are never read by other agents.

### Proof

`evals/promptfoo` runs single-turn cases against `prompts/heartbeat-system.txt`. It has no fixture that persists `AGENT_HOME` across tasks. This design therefore splits the proof in two:

1. Decision-quality evals in promptfoo. Each case gives the agent an index, the relevant entries and a task transcript, and checks the file operations it proposes:
   - Apply: a reviewer's earlier correction is in the index; the agent applies it without being told again.
   - Capture: a reviewer requests changes; the agent writes one entry with a resolvable evidence link.
   - Unlearn: evidence contradicts an entry; the agent retires it with a tombstone and writes the replacement.
   - Quiet success: a routine task with no surprise; the agent writes nothing.
   - Boundary: a task tempts the agent to change its own rules; the agent leaves `AGENTS.md` untouched.
2. Server tests for the read side: the index is added to the run prompt, is capped and truncated as specified, and is absent when no index exists.

A true multi-task end-to-end run with persisted state is out of scope for v1 and is listed as a follow-up.

## Constraints

- Company scope, activity logging and the control-plane invariants in `AGENTS.md` section 5 hold. Files are already company-scoped by `AGENT_HOME`.
- No change to the permission model for v1. The loop relies on an agent's existing right to edit its own files.
- Behavior stays with its owning module: prompt guidance in `agent-instruction-working-copies.ts`, procedure in the `paperclip` skill, and no adapter-specific parsing.
- Storage limits in `doc/agent-files.md` apply (1 MiB entry file, 2 GiB total).

## Decisions made with the owner

- Multiple files per agent instead of one `AGENTS.md`: agreed.
- Learnings stay inside the agent: agreed.
- Learning includes unlearning: agreed.
- The server injects the index into the run prompt, rather than relying on a prompt convention: agreed.

## My calls (not yet reviewed by the owner)

- Capture is gated by "surprise, correction, retry or recovered failure", to keep routine successes from writing memory.
- 90-day staleness threshold, and `stale` entries verified before use rather than auto-retired.
- The agent does not edit `AGENTS.md` through this loop, and enforcement is by skill text only in v1.
- The index cap is a server constant, initial value to be chosen by the builder.
- Rollout is presence-based, with no feature flag: an agent with no `learnings/INDEX.md` gets nothing injected and pays nothing. Agents start learning once the `paperclip` skill step tells them to. The CEO and the Reflection Coach are not special-cased.
- Evidence is checked by the prompt only (links must point at issues or comments in the same company). No write-time validation in v1.
- The server never parses entry frontmatter. It reads `INDEX.md` as opaque text.
- The eval is split into single-turn promptfoo cases plus server tests, because no multi-task fixture with persisted state exists.

## Left to the builder

- Exact index size cap and truncation wording.
- Exact skill wording and where in the `paperclip` skill procedure the step sits.
- Whether the reconcile step runs inline in the task run or as a short follow-up turn, decided by measuring cost and reliability in the eval.
- Slug and filename rules, and whether `INDEX.md` is regenerated by the agent or by a small helper.
- Which run types receive the index. `instructionWorkingCopyGuidance` is called from `server/src/services/heartbeat/instruction-working-copy.ts:221`. The builder verifies that heartbeat, routine, chat and resumed-session runs all pass through it, and covers any that do not.

## Open risks

- An agent can still rewrite its own `AGENTS.md` ungated, since the permission model allows it. If the eval shows the agent drifting into doing so, enforce the boundary in the authorization layer as a follow-up.
- Reflection quality depends on the model. The eval measures this, but it covers two cases, not the range of real tasks.
